# GCB 檢測修復工具 操作手冊

> 修改系統前一定要先建立 VM 快照。

## 事前準備

| 項目 | 需求 |
|---|---|
| VM 作業系統 | RHEL 8 / 9（或 Rocky、Alma）、Ubuntu 22.04 |
| VM 規格 | 2 vCPU、4 GB 記憶體、40 GB 硬碟；Server 版，不含 GUI；已安裝 SSH |
| VM 帳號 | 一個可 SSH 登入、有 sudo 權限的帳號 |
| 你的電腦 | macOS / Linux，可 SSH 連到 VM（Windows 請用附錄 B 的手動部署） |
| 虛擬化平台 | 可建立快照、可開啟主控台（Console） |

## 本手冊的範例值

指令中的值請換成你的實際環境：

| 代稱 | 範例值 | 說明 |
|---|---|---|
| `管理帳號` | `admin` | 你登入 VM 用的帳號（有 sudo 權限） |
| `VM的IP` | `192.168.1.50` | VM 的 IP。在 VM 主控台執行 `hostname -I` 查詢 |
| `測試帳號` | `gcbtest` | 設定精靈中選擇或建立的帳號 |
| `執行編號` | `rhel9-01_20261005_143000` | 每次執行時畫面第一行會顯示（格式：主機名稱_日期_時間） |

每個指令都標示在哪裡執行：

- **💻 你的電腦**：在你的電腦開終端機，先進入 `gcb-checker` 資料夾
- **🖥️ VM**：已經 SSH 登入 VM，並進入 `/opt/gcb-checker`
- **🌐 虛擬化平台**：在 vSphere、Proxmox 等管理介面操作，不是指令

## 修復類型（A / B / C）

每條 GCB 規則依修改後對系統的影響分成三類：

| 類型 | 定義 | 執行方式 | 結果 |
|---|---|---|---|
| **A 類** | 低風險，不影響登入和服務 | `sudo ./gcb.sh run` | 自動修復 |
| **B 類** | 可能影響登入、服務、網路連線，或需要重開機 | `sudo ./gcb.sh run --include-risky` | 加參數才修復；一樣會備份，可以回滾 |
| **C 類** | 無法安全自動化（需人工判斷、需要密碼或環境資訊） | — | 只列入報告，說明人工處理方式 |

**查詢每條規則屬於哪一類：**

| 方式 | 動作 |
|---|---|
| 💻 你的電腦 | 開啟 [規則清單.md](規則清單.md)（各作業系統的完整清單、統計與 C 類無法自動修復的原因） |
| 🖥️ VM | `./gcb.sh rules`（列出這台 VM 適用的規則） |

B 類常見的例子：修改 PAM 登入設定、防火牆、SSH 設定、開機參數、掛載選項、SELinux / AppArmor。

> ⚠️ **B 類中會動到使用者檔案的項目**：Ubuntu 22.04 的 `TWGCB-01-014-0071`（家目錄的 `.rhosts`）。
> 修復時會把每個使用者家目錄下的 `.rhosts` **備份到報告的 `backup/` 目錄後移除**，不會直接刪除。
> - 執行前：如有使用者仍使用 rsh／rlogin，請先通知，或用 `--exclude TWGCB-01-014-0071` 排除這一項
> - 已安裝 rsh／rlogin 服務時，工具不處理，只列入報告
> - 要放回檔案：`sudo ./gcb.sh rollback <執行編號> --rule TWGCB-01-014-0071`（放回原位，權限與擁有者不變）
> - RHEL 的 `.rhosts`、`.shosts` 仍為 C 類，只回報、不處理
C 類常見的例子：獨立分割區、GRUB 開機通行碼、需要判斷用途的檔案與帳號、校時伺服器位址。

部分項目有額外的保護條件，例如偵測到 Docker 時不停用 IP 轉送、會讓帳號密碼立即過期時略過該帳號、UEFI 開機時不停用 fat 檔案系統。這些項目會在報告的備註中說明為什麼略過。

## 操作步驟

### ① 🌐 建立快照

**動作：** 在虛擬化平台建立快照，名稱為 `GCB_before`（各平台操作方式見附錄 A）

**結果：** 可隨時還原到測試前的狀態

### ② 💻 部署並設定

**動作：** 進入工具資料夾，執行部署

```bash
cd ~/Desktop/gcb-checker
```
```bash
./deploy.sh 管理帳號@VM的IP
```

範例：
```bash
./deploy.sh admin@192.168.1.50
```

SSH 不是 22 埠，或要指定金鑰時：
```bash
SSH_OPTS="-o Port=2222 -i ~/.ssh/vm_key" ./deploy.sh admin@192.168.1.50
```

**結果：** 工具安裝到 VM 的 `/opt/gcb-checker`，並自動啟動設定精靈。過程中會詢問 SSH 密碼和 sudo 密碼，請輸入**管理帳號的密碼**。

**設定精靈的問題：**

| 畫面 | 輸入 | 結果 |
|---|---|---|
| `請輸入要使用的帳號（不存在會建立新帳號）［預設 admin］：` | 直接 Enter，或輸入新帳號名稱，例如 `gcbtest` | 新帳號會自動建立並加入 sudo 群組 |
| `新密碼：` / `再輸入一次：` | 測試帳號的密碼（只有建立新帳號時才會問） | 密碼設定完成 |
| `請輸入業務服務：` | 直接 Enter（沒有業務服務），或輸入 `all`，或例如 `nginx,postgresql` | 修復後這些服務停止時，會自動回滾 |
| `✓ 設定完成，可以開始測試。` | — | 進行下一步 |
| `✗ 登入相關檢查未通過` | — | 依畫面上的「↳ 原因／建議」排除後，在 VM 上重新執行設定精靈（見下方） |
| `! 無法使用套件庫：RHEL 尚未註冊訂閱…` | — | 需安裝套件的項目（aide、auditd 等）會無法修復；先執行 `sudo subscription-manager register` 或設定內部鏡像站，再重新執行設定精靈 |

在 VM 上重新執行設定精靈：
```bash
cd /opt/gcb-checker && sudo ./setup.sh
```

### ③ 💻 確認測試帳號可登入

**動作：** 另開一個終端機視窗，用測試帳號登入 VM

```bash
ssh 測試帳號@VM的IP
```

範例：
```bash
ssh gcbtest@192.168.1.50
```

登入後執行：
```bash
sudo -v
```

**結果：** 兩個都成功、沒有錯誤訊息，就代表測試帳號可用。執行 `exit` 離開。

### 登入 VM（④–⑨ 都在 VM 上執行）

```bash
ssh 管理帳號@VM的IP
```

範例：
```bash
ssh admin@192.168.1.50
```

登入後進入工具目錄：
```bash
cd /opt/gcb-checker
```

### ④ 🖥️ 檢測

**動作：**
```bash
sudo ./gcb.sh check
```

**結果：** 產出 `GCB不合格清單_*.xlsx`（不合格清單報告），不修改系統

### ⑤ 🖥️ 預覽修改內容（不會修改系統）

**動作：**
```bash
sudo ./gcb.sh run --dry-run --include-risky
```

**結果：** 列出會修改的內容，不修改系統。如果有不能修改的項目，把它的 TWGCB-ID 加到 `config.ini` 的 `exclude_rules`：

```bash
sudo vi /opt/gcb-checker/config.ini
```

範例（排除 IP 轉送和 SSH 禁止 root 登入）：
```ini
exclude_rules = TWGCB-01-012-0108,TWGCB-01-012-0269
```

### ⑥ 🖥️ 修復 A 類（項目見「修復類型」）

**動作：**
```bash
sudo ./gcb.sh run
```

**結果：** 依序出現以下畫面：

| 畫面 | 輸入 | 結果 |
|---|---|---|
| `確定開始修復？已建議先建立 VM 快照。[y/N]` | `y` | 開始修復，完成後自動執行後測 |
| `… TWGCB-…：安裝套件 auditd — 可能需要數分鐘，請稍候` | — | 安裝套件、初始化 AIDE 資料庫（10–30 分鐘）等耗時步驟開始，**不要中斷** |
| `… 仍在執行：修復 TWGCB-…（已 2 分 30 秒）` | — | 每 30 秒出現一次，表示仍在進行，**不要中斷** |
| `登入是否正常？[y=正常 / n=異常，將回滾]` | 先做下方的「人工登入確認」，再回來輸入 | 輸入 `y`：修改保留；輸入 `n`：全部回滾 |
| `修復情況報告：.../GCB修復報告_*.xlsx` | — | 完成，記下畫面上的執行編號 |

**人工登入確認：** 原本的視窗**不要關**，另開一個終端機視窗執行：
```bash
ssh gcbtest@192.168.1.50
```
```bash
sudo -v
```
兩個都成功，回到原視窗輸入 `y`；任一個失敗，回到原視窗輸入 `n`。

### ⑦ 🌐 建立快照

**動作：** 在虛擬化平台建立快照，名稱為 `GCB_A_done`

**結果：** 可還原到 A 類修復後的狀態

### ⑧ 🖥️ 修復 B 類（項目見「修復類型」）

**動作：**
```bash
sudo ./gcb.sh run --include-risky
```

**結果：** 和 ⑥ 相同，一樣要做人工登入確認。修復後 **root 無法再用 SSH 登入**，請改用管理帳號或測試帳號登入。

Ubuntu 會一併移除使用者家目錄的 `.rhosts`（已備份，可回滾放回），詳見「修復類型」的說明。

### ⑨ 🖥️ 重開機後驗證

**只有畫面最後出現「部分項目需重開機生效」時才需要做。**

**動作：** 重開機
```bash
sudo reboot
```

等待約 1–2 分鐘後重新登入：
```bash
ssh admin@192.168.1.50
```

執行驗證（執行編號用 ⑧ 畫面上顯示的編號）：
```bash
cd /opt/gcb-checker
```
```bash
sudo ./gcb.sh verify 執行編號
```

範例：
```bash
sudo ./gcb.sh verify rhel9-01_20261005_143000
```

忘記執行編號時，用這個指令查詢：
```bash
./gcb.sh list
```

**結果：** 修復報告加上「重開機後驗證」工作表

### ⑩ 💻 取回報告

**動作：** 回到你的電腦，執行：
```bash
cd ~/Desktop/gcb-checker
```
```bash
./deploy.sh 管理帳號@VM的IP fetch
```

範例：
```bash
./deploy.sh admin@192.168.1.50 fetch
```

**結果：** 報告下載到 `gcb-checker/vm-reports/192.168.1.50_日期時間/`，不含系統備份檔。回報這個資料夾，並附上異常畫面的截圖。

出現 `無法連線 VM`：GCB 修復後 SSH 登入等待時間縮短為 60 秒、驗證失敗次數上限為 4 次。請在密碼提示出現後 60 秒內輸入，重新執行一次；仍失敗時先用 `ssh 管理帳號@VM的IP` 互動登入確認。

### ⑪ 🌐 還原快照

**動作：** 在虛擬化平台還原快照 `GCB_before`

**結果：** VM 回到測試前的狀態，可以重新測試

指令中的值請換成實際環境，範例值見「本手冊的範例值」。

### 💻 你的電腦（在 `gcb-checker` 資料夾內執行）

| 用途 | 指令 | 範例 | 修改 VM |
|---|---|---|---|
| 部署工具並啟動設定精靈 | `./deploy.sh 管理帳號@VM的IP` | `./deploy.sh admin@192.168.1.50` | 安裝工具 |
| 部署（指定 SSH 埠或金鑰） | `SSH_OPTS="-o Port=埠號 -i 金鑰檔" ./deploy.sh 管理帳號@VM的IP` | `SSH_OPTS="-o Port=2222 -i ~/.ssh/vm_key" ./deploy.sh admin@192.168.1.50` | 安裝工具 |
| 取回報告到 `vm-reports/` | `./deploy.sh 管理帳號@VM的IP fetch` | `./deploy.sh admin@192.168.1.50 fetch` | 否 |

### 🖥️ VM（在 `/opt/gcb-checker` 內執行）

**設定與查詢**

| 用途 | 指令 | 範例 | 修改系統 |
|---|---|---|---|
| 設定精靈（問答式） | `sudo ./setup.sh` | `sudo ./setup.sh` | 可能建立測試帳號 |
| 設定精靈（直接指定，不詢問） | `sudo ./setup.sh --user 測試帳號 --services 服務1,服務2` | `sudo ./setup.sh --user gcbtest --services nginx,postgresql` | 可能建立測試帳號 |
| 列出本機適用的規則 | `./gcb.sh rules` | `./gcb.sh rules` | 否 |
| 列出歷次執行編號 | `./gcb.sh list` | `./gcb.sh list` | 否 |
| 查看所有指令說明 | `./gcb.sh --help` | `./gcb.sh run --help` | 否 |
| 確認 sudo 權限 | `sudo -v` | `sudo -v` | 否 |
| 查詢 VM 的 IP | `hostname -I` | `hostname -I` | 否 |

**檢測與修復**

| 用途 | 指令 | 範例 | 修改系統 |
|---|---|---|---|
| 只做健康檢查 | `sudo ./gcb.sh health` | `sudo ./gcb.sh health` | 否 |
| 檢測，產出不合格清單 | `sudo ./gcb.sh check` | `sudo ./gcb.sh check` | 否 |
| 預覽修改內容（A 類） | `sudo ./gcb.sh run --dry-run` | `sudo ./gcb.sh run --dry-run` | 否 |
| 預覽修改內容（A + B 類） | `sudo ./gcb.sh run --dry-run --include-risky` | `sudo ./gcb.sh run --dry-run --include-risky` | 否 |
| 修復 A 類 | `sudo ./gcb.sh run` | `sudo ./gcb.sh run` | **是** |
| 修復 A + B 類 | `sudo ./gcb.sh run --include-risky` | `sudo ./gcb.sh run --include-risky` | **是** |
| 修復時排除指定規則 | `sudo ./gcb.sh run --exclude TWGCB-ID ...` | `sudo ./gcb.sh run --exclude TWGCB-01-012-0108 TWGCB-01-012-0269` | **是** |
| 重開機後驗證 | `sudo ./gcb.sh verify 執行編號` | `sudo ./gcb.sh verify rhel9-01_20261005_143000` | 否 |

**回滾**

| 用途 | 指令 | 範例 | 修改系統 |
|---|---|---|---|
| 回滾整次修改 | `sudo ./gcb.sh rollback 執行編號` | `sudo ./gcb.sh rollback rhel9-01_20261005_143000` | **是**（還原） |
| 只回滾一條規則 | `sudo ./gcb.sh rollback 執行編號 --rule TWGCB-ID` | `sudo ./gcb.sh rollback rhel9-01_20261005_143000 --rule TWGCB-01-012-0269` | **是**（還原） |

**`run` 的其他參數**（一般不需要使用）

| 參數 | 用途 | 注意 |
|---|---|---|
| `-y` | 不詢問「確定開始修復？」直接修復 | 建議先用 `--dry-run` 確認過再用 |
| `--no-manual-confirm` | 略過修復後的人工登入確認 | 不建議，人工確認是最後一道防線 |
| `--skip-login-test` | 沒有設定測試帳號時仍繼續 | **不建議**，無法自動確認修復後可登入 |
| `--force` | 前測登入項目失敗時仍繼續 | **不建議**，可能修復後無法登入 |
| `-c 設定檔路徑` | 使用其他設定檔（所有指令都可用，放在子指令前） | 範例：`sudo ./gcb.sh -c /root/my.ini check` |

## 回滾

| 情況 | 結果 |
|---|---|
| 測試通過，人工確認輸入 `y` | **不回滾**，修改保留 |
| 某一條規則修復失敗 | 只還原那一條，其他保留 |
| 後測時關鍵項目退步 | 自動全部回滾 |
| 人工確認輸入 `n` | 全部回滾 |

手動回滾（整次或單一規則）的指令見「指令大全」的**回滾**。修復成功後備份仍會保留，之後發現影響業務也可以回滾。

**清理報告前注意：** 回滾需要修復報告資料夾裡的 `rollback.json` 與 `backup/`，刪除後就無法用 `./gcb.sh rollback` 還原，只能還原 VM 快照。

| 報告資料夾（`/opt/gcb-checker/reports/`） | 可以刪除嗎 |
|---|---|
| `check_…`、`health_…` | 可以（只有報告） |
| 修復（`主機名稱_日期時間`），已確認不需回滾 | 可以 |
| 修復，之後可能還要回滾 | **不要刪** |

要留存報告，先以 `./deploy.sh 管理帳號@VM的IP fetch` 取回再刪除（取回的檔案不含備份與回滾紀錄）。

## 異常處理

| 狀況 | 動作 |
|---|---|
| `deploy.sh` 出現 `Permission denied` | 先確認能登入：`ssh admin@192.168.1.50` |
| `deploy.sh` 出現 `Connection timed out` | 確認 IP 正確、VM 已開機、防火牆有開放 22 埠 |
| 「前測登入相關項目失敗，停止修復」 | 依「↳ 原因／建議」排除後重新執行 |
| 「未設定 test_user」 | 🖥️ `sudo ./setup.sh` |
| 報告中有「修復失敗」 | 不用處理，該項已自動還原；查看報告的「可能原因與建議」欄位並回報 |
| 執行中斷（Ctrl+C、斷線） | 🖥️ `sudo ./gcb.sh rollback 執行編號` |
| SSH 登不進去 | 🌐 從主控台登入 VM，執行 `rollback`；不行就還原快照 |
| 無法開機 | 🌐 還原快照 |

## config.ini

設定精靈會自動填寫。以下情況才需要手動修改：

```bash
sudo vi /opt/gcb-checker/config.ini
```

| 欄位 | 什麼時候改 | 範例 |
|---|---|---|
| `exclude_rules` | 有不能修改的項目 | `exclude_rules = TWGCB-01-012-0108` |
| `dns_test_name` | 要測試 DNS 解析 | `dns_test_name = www.google.com` |
| `package_timeout` | 安裝套件逾時 | `package_timeout = 600` |
| `firewall_backend` | 系統同時裝了多套防火牆、自動判斷不準確 | `firewall_backend = firewalld`（可用 auto、firewalld、nftables、iptables、ufw） |

重新執行 `deploy.sh` 時，VM 上的 `config.ini` 和 `reports/` 會保留。

## 附錄 A：快照操作

快照名稱請用英文（Proxmox 不支援中文）。有「包含記憶體」的選項時請勾選，還原後會直接回到開機中的狀態。

| 平台 | 建立快照 | 還原快照 |
|---|---|---|
| VMware vSphere（vCenter） | 對 VM 按右鍵 → 快照 → 建立快照 → 輸入名稱、勾選「建立虛擬機器記憶體的快照」→ 建立 | 對 VM 按右鍵 → 快照 → 管理快照 → 選擇快照 → 還原 |
| VMware ESXi（Host Client） | 對 VM 按右鍵 → Snapshots → Take snapshot → 輸入名稱 → Take snapshot | 對 VM 按右鍵 → Snapshots → Manage snapshots → 選擇快照 → Restore snapshot |
| Proxmox VE | 選擇 VM → Snapshots 分頁 → Take Snapshot → 輸入名稱、勾選 Include RAM → Take Snapshot | 選擇 VM → Snapshots 分頁 → 選擇快照 → Rollback |
| VirtualBox | 選擇 VM → 快照 → 製作 → 輸入名稱 → 確定 | **先將 VM 關機** → 快照 → 選擇快照 → 還原 |
| Hyper-V | 對 VM 按右鍵 → 檢查點 → 在「檢查點」清單中對新檢查點按右鍵 → 重新命名 | 在「檢查點」清單中對檢查點按右鍵 → 套用 |
| KVM（virt-manager） | 開啟 VM 視窗 → 檢視 → 快照 → 左下角「+」→ 輸入名稱 → 完成 | 快照清單中選擇快照 → 左下角「▶」執行 |

測試結束後請刪除不需要的快照，否則會占用磁碟空間並拖慢 VM。快照不是備份，VM 磁碟損壞時快照也會一起失效。

## 附錄 B：手動部署（Windows 或連不到 VM 時）

**1. 💻 打包**（在 `gcb-checker` 的上一層資料夾執行）
```bash
cd ~/Desktop
```
```bash
tar czf gcb-checker.tar.gz --exclude=docs --exclude=tools --exclude=samples --exclude=tests --exclude=reports --exclude=vm-reports --exclude=.idea gcb-checker
```
結果：產生 `~/Desktop/gcb-checker.tar.gz`

**2. 💻 傳到 VM 的 `/tmp/`**（也可以用 WinSCP、共用資料夾或 USB）
```bash
scp gcb-checker.tar.gz admin@192.168.1.50:/tmp/
```
結果：檔案在 VM 的 `/tmp/gcb-checker.tar.gz`

**3. 🖥️ 安裝並啟動設定精靈**
```bash
sudo tar xzf /tmp/gcb-checker.tar.gz -C /opt
```
```bash
sudo chown -R root:root /opt/gcb-checker
```
```bash
cd /opt/gcb-checker && sudo ./setup.sh
```
結果：安裝完成，並啟動設定精靈（問題同步驟 ②）

**4. 🖥️ 測試完成後打包報告**（不含系統備份檔）
```bash
cd /opt/gcb-checker && sudo tar czf /tmp/gcb-reports.tar.gz --exclude=backup --exclude=rollback.json reports && sudo chmod 644 /tmp/gcb-reports.tar.gz
```
結果：產生 `/tmp/gcb-reports.tar.gz`

**5. 💻 下載報告**
```bash
scp admin@192.168.1.50:/tmp/gcb-reports.tar.gz ~/Desktop/
```
結果：報告在 `~/Desktop/gcb-reports.tar.gz`
