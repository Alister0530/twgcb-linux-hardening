# 開發指南

給維護程式、新增規則或新增作業系統的開發人員。操作方式見 [操作手冊.md](操作手冊.md)，各規則的分類見 [規則清單.md](規則清單.md)。

## 專案架構

```
gcb-checker/
├── README.md              入口與文件索引
├── LICENSE                MIT 授權
├── deploy.sh              在操作人員的電腦執行：部署到 VM、取回報告
├── setup.sh               在 VM 執行：設定精靈
├── gcb.sh                 在 VM 執行：主程式入口（尋找 Python 後執行 gcb.py）
├── gcb.py                 指令解析，分派到各功能
├── config.ini             設定檔（由設定精靈填寫）
├── gcb/

│   ├── report.py          產生兩份 Excel 報告

│   ├── pkgsvc.py          套件、服務、核心參數的查詢
│   ├── textedit.py        設定檔文字處理（純函式）

│   ├── config.py          讀取 config.ini
│   ├── util.py            共用工具
│   └── rules/
│       ├── base.py        規則基礎類別、無法自動修復原因的分類
│       ├── generic.py     通用規則類型（掛載選項、設定檔參數、檔案權限、稽核規則…）
│       ├── common.py      跨作業系統共用規則
│       ├── ubuntu/        Ubuntu 規則（disk、system、network、audit、access、optional）
│       └── rhel/          RHEL 8 / 9 共用規則（disk、system、network、logging、selinux、accounts、ssh）
├── docs/
│   ├── 操作手冊.md         操作人員：從拿到 VM 到回報結果
│   ├── 開發指南.md         本文件
│   ├── 規則清單.md         各平台規則清單（tools/gen_rule_list.py 自動產生）
│   ├── 決策紀錄.md         規格模糊時的判定原則與個別決定
│   ├── gcb/<平台>/         GCB 官方 PDF 與切分後的原文 chunks.json（不納入版本控制，下載方式見 gcb/README.md）
│   └── specs/<規則套件>/   每條規則的分析規格；rhel/編號對照.md 為 RHEL 8 / 9 編號對照
├── tools/
│   ├── gcb_pdf_split.py   切分 GCB PDF
│   ├── gen_rule_list.py   從程式碼產生 docs/規則清單.md
│   ├── coverage.py        測試涵蓋率（只用標準函式庫）
│   └── push_all.sh        推送到 GitLab（完整歷史）與 GitHub（公開，只推目前內容）
├── samples/               範例報告
```

`deploy.sh` 只部署程式與設定檔，不部署 `docs/`、`tools/`、`samples/`、`tests/`。

執行時產生：VM 上的 `reports/`（每次執行的報告、log、備份），操作人員電腦上的 `vm-reports/`（`deploy.sh fetch` 取回的報告）。

## 執行流程（`gcb.sh run`）

| 階段 | 做什麼 | 程式 |
|---|---|---|
| 1. 前測 | 19 項健康檢查；登入相關項目（H01–H06）失敗就停止 | `health.py` |
| 2. 檢測 | 逐條檢測，產出 `GCB不合格清單_*.xlsx` | `engine.do_detect`、各規則的 `check()` |
| 3. 規劃 | 依修復類型、`--include-risky`、`exclude_rules`、前置條件決定每條的處理方式 | `engine.plan_fixes` |
| 4. 修復 | 依編號修復（`run_last` 的規則最後執行）；每個動作先寫回滾紀錄，修完立即重新檢測，不合格就只還原該條 | `engine.apply_rule`、`fixer.Fx`、`journal.py` |
| 5. 後測 | 重跑健康檢查與檢測；關鍵項目退步就自動全部回滾；接著人工登入確認 | `health.compare`、`engine.rollback_all` |
| 6. 報告 | 產出 `GCB修復報告_*.xlsx` | `report.py` |

每次執行的輸出目錄 `reports/<執行編號>/`（權限 700）：

| 檔案 | 內容 |
|---|---|
| `GCB不合格清單_*.xlsx` | 摘要、不合格清單、全部檢測結果、前測健康檢查 |
| `GCB修復報告_*.xlsx` | 摘要（合規率前後對照）、修復明細、健康檢查對照、修復步驟紀錄、重開機後驗證 |
| `remediation.log` | 每一步的指令、修改前後差異、結果 |
| `backup/`、`rollback.json` | 備份檔與回滾紀錄 |
| `state.json` | 執行狀態（verify、rollback 會用到） |

錯誤訊息的中文說明在 `gcb/hints.py`（正規表示式 → 原因、建議），遇到新的錯誤訊息直接加入對照表。

## 規則寫法

| 項目 | 規範 |
|---|---|
| 註解 | 每條規則上方 `# NNNN 項目名稱`（RHEL：`# RHEL8 NNNN / RHEL9 NNNN 項目名稱`）；客製類別上方 `# [類別名稱] TWGCB-01-0XX-NNNN 項目名稱` |
| 編號 | Ubuntu 用 `ubuntu/helpers.py` 的 `U(n)`；RHEL 用 `rhel/helpers.py` 的 `R(r8=, r9=)`；同一項規則多個版本共用一個物件 |
| 欄位 | `title` 照 GCB 原則設定名稱、`expected` 照 GCB 設定值、`category` 照 GCB 類別、`risk` 為 A/B/C |
| 檢測 | `check()` 不可修改系統；需重開機才生效的項目以「設定已正確」判定合格，並設 `needs_reboot = True` |
| 修復 | 所有修改透過 `fx`（見下方「修復動作（Fx）」） |
| 失敗 | 修復失敗 `raise FixError`；需要人工 `raise ManualRequired`（繁體中文，說明原因與做法） |
| C 類 | 實作 `check()` 與 `manual_hint`（人工處理方式），不寫 `fix()`；無法自動修復的原因由 `base.manual_reason_for()` 依說明分類，分類不準時在規則設定 `manual_reason` |
| 適用條件 | 不適用時用 `when`（回傳原因字串）；修復前的安全檢查用 `precondition()` |
| 不適用原因 | 寫成「事實＋為什麼不需檢查」，例：`未安裝 sudo，沒有 sudo 設定需要檢查`、`GCB 防火牆規則…三選一；本機採用 UFW（依據：…），本項目屬 Nftables，不需設定` |
| 判定原則 | 遵守 [決策紀錄.md](決策紀錄.md) |
| Python | 必須相容 3.6（RHEL 8 的 platform-python）：不用 dataclass、walrus、subprocess 的 `capture_output`／`text` |

### 修復動作（Fx）

`fix(ctx, fx)` 不直接修改系統，一律呼叫 `fx` 的方法。每個方法會自動：修改前備份並寫入回滾紀錄 → 寫 log → `--dry-run` 時只記錄不修改。

| 方法 | 修改內容 | 回滾方式 |
|---|---|---|
| `fx.write_file(path, text)`／`fx.edit_file(path, func)` | 寫入／改寫檔案 | 放回備份（含權限、擁有者）；原本不存在則刪除 |
| `fx.backup_only(path)` | 只備份（之後由外部指令改寫或自行移除） | 放回備份 |
| `fx.backup_dir(path)` | 備份整個目錄 | 清空後以備份還原 |
| `fx.chmod(path, mode)`／`fx.chown(path, uid, gid, label)` | 權限、擁有者 | 改回原值 |
| `fx.service_mask(unit)`／`fx.service_enable(unit)` | 停用／啟用服務 | 恢復原 enabled／active 狀態 |
| `fx.pkg_install(pkg)`／`fx.pkg_remove(pkg)` | 安裝／移除套件 | 移除本次新增的套件（含相依）／裝回 |
| `fx.sysctl_set(key, value)` | 核心參數（執行中） | 設回原值 |
| `fx.chage(user, opt, old, new)` | 帳號通行碼期限 | 設回原值 |
| `fx.run(cmd, desc)` | 執行外部指令（只寫 log） | **無**，需搭配 `fx.add_undo()` |
| `fx.run_tracked(cmd, desc, paths)` | 執行會改檔案的外部指令，log 記錄檔案差異 | **無**，需先 `backup_only` 或 `add_undo()` |
| `fx.step(action, detail)`／`fx.note(text)` | 只寫 log／備註（備註會出現在報告） | — |

**外部指令的回滾：先登記、再執行**

```python
fx.backup_only("/etc/authselect/system-auth")                                         # ① 備份
fx.add_undo(["authselect", "disable-feature", "with-faillock"], "停用 with-faillock")  # ② 登記回滾指令
fx.run(["authselect", "enable-feature", "with-faillock"], "啟用 with-faillock")        # ③ 執行
```

- 先登記：指令中途失敗或逾時，自動回滾仍會執行還原指令
- 回滾依登記的反向順序：上例先 ② `disable-feature`，再 ① 放回備份
- 「重新載入」類回滾（`daemon-reload`、`reload`、`restart`、`augenrules --load`）一律在**修改檔案之前**登記，回滾時才會在檔案還原之後執行、讀到原設定；`tests/test_lint.py` 會檢查所有規則

**禁止**：在 `fix()` 內直接 `open()` 寫檔、`subprocess` 執行指令、`os.remove` 刪檔而未先 `fx.backup_only()`。後果：沒有備份無法回滾、log 與報告看不到、`--dry-run` 也會真的修改。

自行修改檔案時（例如 0071 移除 `.rhosts`），先 `fx.backup_only()`、`if fx.dry:` 只記錄預覽，實際修改後用 `fx.step()` 寫 log。

修改規則後執行：

```bash
python3 -m unittest discover -s tests
```
```bash
python3 tools/gen_rule_list.py
```

## 測試

| 測試 | 指令 | 驗證範圍 |
|---|---|---|
| 單元測試 | `python3 -m unittest discover -s tests` | 文字處理、稽核規則比對、Excel、錯誤說明；規則與 GCB 原文一一對應且名稱一致、C 類都有原因與處理方式；各平台規則的輔助函式；`tests/test_lint.py`：同名函式覆蓋、回滾登記順序 |
| 流程情境測試 | 包含在單元測試（`tests/test_engine_flow.py`） | 用假規則與假健康檢查驗證主流程：只修 A 類、`--include-risky`、`--exclude`、預覽、取消、前測失敗停止、未設定測試帳號、自動回滾、人工確認 y / n、`verify`、單一規則回滾、`run_last` 順序 |
| 容器完整測試 | `tests/docker_test.sh ubuntu:22.04`（或 `rockylinux:8`、`rockylinux:9`） | 在容器內跑 check → run --include-risky → rollback，並比對回滾後的 `/etc` |
| 容器情境測試 | `tests/docker_scenarios.sh ubuntu:22.04`（同上三種） | 依操作手冊順序用真實規則測試：setup.sh、health、rules、list、check、預覽不得修改 `/etc`、只修 A 類、單一規則回滾、verify、整次回滾 |
| x86_64 測試 | 在指令前加 `PLATFORM=linux/amd64`，例如 `PLATFORM=linux/amd64 tests/docker_test.sh rockylinux:9` | 在 ARM 主機上模擬 x86_64（較慢），涵蓋 32 位元（b32）稽核規則 |
| VM 實測 | 依 [操作手冊.md](操作手冊.md) | systemd、開機、SELinux / AppArmor、核心參數、防火牆等容器無法驗證的項目 |

容器沒有 systemd、GRUB、SELinux，也不能改核心參數，這些項目在容器內修復失敗（並自動還原）屬正常。`samples/` 的範例報告也是在容器中產生，報告中這類「修復失敗」同樣屬於容器限制。

涵蓋率：單元測試以 `tests/fakes.py` 的模擬環境（`FakeCtx`、`FakeFx`、`FakeRunner`）取代真實指令與檔案，不需容器即可涵蓋所有修復路徑

```bash
python3 tools/coverage.py report
```
```bash
python3 tools/coverage.py missing gcb/rules/rhel/ssh.py
```

2026-10-06 結果：單元測試 1180 項，行涵蓋率 100%（11101 行）。新增規則時請一併補測試，維持 100%；容器測試前加 `COV_DIR=$PWD/tests/out/cov` 可再合併容器實跑的結果（`report tests/out/cov`）。

單元測試必須同時在 Python 3.6 通過（RHEL 8 的 platform-python）：

```bash
docker run --rm -v "$PWD":/src:ro rockylinux:8 sh -c 'cp -r /src /tmp/g && cd /tmp/g && /usr/libexec/platform-python -m unittest discover -s tests'
```

## 版本控制與推送

兩個資料夾各自保有自己的歷史，不需強制推送：

| 資料夾 | 遠端 | 內容 |
|---|---|---|
| `gcb-checker`（本專案） | 公司 GitLab（`gitlab`） | 完整歷史，日常開發在這裡 |
| `gcb-checker-public`（與本專案同層） | 公開 GitHub（MIT） | 由腳本同步，作者為個人帳號；不含 GCB 官方 PDF、`chunks.json` 與公司資訊 |

在本專案修改並 commit 後，一行指令推送兩邊：

```bash
tools/push_all.sh
```

只預覽不推送：

```bash
tools/push_all.sh --dry-run
```

腳本流程：推送 GitLab → 把版本控制內的檔案同步到公開版資料夾 → 檢查（無 PDF、`chunks.json`、公司網域）→ 在公開版跑單元測試 → commit（說明列出本次同步的 commit 主旨）→ 推送 GitHub。任一檢查不通過就中止，並還原公開版資料夾。公開版不要直接修改，否則下次同步會被覆蓋。

## 新增作業系統

以新增 Ubuntu 24.04（假設 GCB 文件編號為 TWGCB-01-0XX）為例。框架與作業系統無關，新增作業系統**只需要新增規則**；同系列的不同版本共用同一個規則套件。

| # | 動作 | 結果 |
|---|---|---|
| 1 | 把官方 PDF 放到 `docs/gcb/ubuntu2404/` | 文件歸檔 |
| 2 | `python3 tools/gcb_pdf_split.py docs/gcb/ubuntu2404/<PDF> docs/gcb/ubuntu2404/chunks.json` | 每條規則切成一段原文；確認條數與文件「項數統計」表相同、沒有缺號或重複 |
| 3 | 在 `gcb/platforms.py` 的 `PLATFORMS` 加一列：`Platform("ubuntu2404", "debian", ("ubuntu",), "24.04", "0XX", "<文件名稱>", "ubuntu", "ubuntu:24.04")` | 工具能辨識新系統，規則套件指向既有的 Ubuntu 套件 |
| 4 | 與同系列前一版的原文對照，整理規格到 `docs/specs/<規則套件>/`。**依編號與項目名稱對照，不要依類別條數切範圍**：新版新增的項目常排在最後，編號也可能整段位移（範例：`docs/specs/rhel/編號對照.md`） | 找出兩版相同、不同、新增的項目，並寫編號對照表 |
| 5 | 相同的規則：在既有規則加上新版本編號，例如 `rule_ids(ubuntu2204=2, ubuntu2404=3)` | 一條規則同時支援兩版 |
| 6 | 不同或新增的規則：用 `rule_ids(ubuntu2404=N)` 只給新版本編號 | 只在新版本生效 |
| 7 | 單元測試、`python3 tools/gen_rule_list.py` | 檢查新平台、更新 `docs/規則清單.md` |
| 8 | `tests/docker_test.sh ubuntu:24.04`，再到 VM 實測 | 驗證檢測、修復、回滾 |
| 9 | 更新 `README.md` 的支援系統表與 `docs/操作手冊.md` 的事前準備 | 文件同步 |

全新的系列（例如 Debian、SUSE）：`Platform` 的 `family` 決定套件管理與 PAM 的處理方式，需在 `gcb/pkgsvc.py` 與相關規則加入該系列的處理，並新增 `gcb/rules/<系列>/` 規則套件。

## 已知限制

- 回滾時會移除修復時安裝的套件（含連帶安裝的相依套件），但以下無法還原：
  - 套件安裝腳本建立的系統帳號，例如 Ubuntu 安裝 rsyslog 時建立的 `syslog` 帳號。
  - 被升級的相依套件不會降版。
  - 部分套件安裝後留下的目錄，例如 `/etc/audit`、`/etc/cron.hourly`。
- 回滾時重新安裝已移除的套件，需要能連線到套件庫。
- 稽核規則設為不可變更（`-e 2`）後，任何稽核規則的修改與回滾都要重開機才生效。

## 待整理

- `rhel/disk.py` 從 `ubuntu/system.py` 借用了 10 個與作業系統無關的工具函式（`efi_status`、`proc_mounts`、`sysctl_fix` 等），應移到 `generic.py`。
- sysctl 有三套寫法（`common.NetSysctl` 系列、`ubuntu/network.py`、`rhel/network.py`），可統一為一個以 `sysctl_override_path` 為基礎的類別。
- 全檔案系統掃描（無擁有者檔案、SUID/SGID、world-writable、特權指令）各自執行 `find /`，可合併成一次掃描共用結果以縮短檢測時間。
- Ubuntu PAM 相關工具函式（common-password／common-auth 解析）在 `ubuntu/access.py` 與 `common.py` 各有一份。
- GRUB 核心參數規則有 `common.GrubArg` 與 `ubuntu/access.py` 的 `GrubArgs` 兩種實作。
- 稽核規則的 syscall 過濾（`audit_filter_syscalls`）在 Ubuntu 與 RHEL 各有一次重複呼叫，可在 `generic.AuditRules` 統一處理。
- RHEL 8 0040/0041、0111–0116、0124–0125 目前為區分標題而拆成不同物件；改用 `TITLE_OVERRIDES` 後可合併。
